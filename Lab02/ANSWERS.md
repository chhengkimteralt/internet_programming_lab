# Week 5 Practice: Building a Single-Page App - Answers

### 1. You refresh the browser on `/events/2` and the page loads. Which program answered that request in development, and what must the production server do so it still works after deployment?
In development, the Vite development server answers that request by falling back to serve `index.html` regardless of the URL path thanks to its built-in SPA history fallback middleware. In production, a static web server (such as Nginx, Apache, or Caddy) would look for a physical file or folder at `/events/2` and return a 404 Not Found error. To fix this, the production server must be configured with URL rewriting to fall back to `index.html` for any route that does not match a real file, allowing Vue Router on the client to parse the path and render `EventDetailPage`.

### 2. The guard stops students from opening `/events/new`. Can a student still create an event? How, and what must stop them?
Yes, a student can still create an event because client-side route guards only control UI navigation and provide no real security. A student could switch their role in Pinia/DevTools or bypass the browser interface entirely by sending an HTTP POST request directly to `/events` using tools like `curl`, Postman, or the browser console's `fetch()`. The backend server must enforce authorization checks by validating user identity/session tokens and rejecting unauthorized event creation attempts with HTTP 401 Unauthorized or 403 Forbidden.

### 3. EventDetailPage loads its event in a watch on the id with immediate: true, not in onMounted. What bug would onMounted alone cause?
`onMounted` executes only once when the component is initially created and inserted into the DOM. When a user navigates between two routes that share the same component (such as navigating from `/events/1` to `/events/2`), Vue reuses the existing component instance for performance rather than unmounting and remounting it. With `onMounted` alone, the component would never reload the new event data when the `id` prop updates; using `watch` with `immediate: true` ensures the event is fetched both on initial mount and whenever the `id` prop changes.

### 4. Why does EventsPage use storeToRefs(store) instead of const { events } = store?
In Pinia, store state properties are reactive properties on a reactive proxy; destructuring them directly with `const { events } = store` strips away their reactivity by extracting raw values, so subsequent updates (like fetching events) will not trigger component re-renders. `storeToRefs(store)` creates `ref`s for each state property and getter while maintaining their reactive connection to the Pinia store. It enables safe destructuring of reactive state without breaking reactivity and keeps action methods directly callable on the store.

### 5. Booking makes two requests: POST the booking, then PATCH the seat count. What happens to the data if the second one fails? How could the server avoid this?
If the POST request succeeds but the PATCH request fails (for instance due to network loss, server crash, or validation failure), the database is left in an inconsistent state: a booking record exists, but the event's `booked` count was never updated, leading to overselling or mismatched seat counts. The server could avoid this by handling both operations as a single atomic transaction inside one backend endpoint (e.g. POST `/bookings` automatically creates the booking record and increments the event's booked count inside an ACID database transaction), rolling back entirely if any part fails.
